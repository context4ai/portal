# 测评评分与计时标准

<!-- context:section id="overview" -->
本页是[评测知识库效果](./evaluating-your-knowledge-base.md)所引用的规则手册。可以原样采用，也可以调整后注明改了什么。它涵盖单个回答如何判分、判分如何变成比率，以及耗时和工具调用如何测量。[知识检索测评](../../architecture/benchmark/knowledge-retrieval.md)就采用了这套标准。
<!-- /context:section -->

<!-- context:section id="industry" -->
## 参考的业界方法

本标准借鉴了已发表的工作。四档结果、采样和记录约定是本项目自己的选择，并非业界统一标准。

| 来源 | 借鉴之处 |
| --- | --- |
| [SimpleQA](https://openai.com/index/introducing-simpleqa/)（OpenAI） | 把回答分为正确、错误和未作答，并单独统计“未作答”，使拒答既不算错误也不算成功。 |
| [FACTS Grounding](https://deepmind.google/blog/facts-grounding-a-new-benchmark-for-evaluating-the-factuality-of-large-language-models/)（Google DeepMind） | 先判断回答是否回应了请求，再核验其事实依据——两项分开判定。 |
| [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)（Anthropic） | 按结果评价 Agent，而不是按固定的工具顺序或路径；保留完整轨迹用于解释结果。 |
| [Ragas Factual Correctness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/factual_correctness/) 与 [Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) | 区分“与参考事实一致”和“与检索到的材料一致”：材料可能过时或漏掉条件，所以忠实于材料不等于正确。 |
| [Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena](https://arxiv.org/abs/2306.05685) | 模型评审存在位置偏差、冗长偏差和自我偏好；需要交换顺序、匿名化并用校准样例检查。 |
| 最近秩法（nearest-rank）百分位 | P90 取排序后的第 ⌈0.9 × n⌉ 个样本，因此这个数字总是一次真实、可复核的运行。 |

<!-- context:section id="metrics" -->
## 两个主指标与实质错误

| 指标 | 判定内容 | 记录值 |
| --- | --- | --- |
| 核心结论正确性 | 给出的关键结论在题目范围内是否成立？是否缺少会让结论产生误导的条件？ | 正确 / 实质错误 / 无可判定结论 / 待核验 |
| 原问需求满足程度 | 用户要求的内容是否真正交付？只按问题本身及其必要上下文判断。 | 完全 / 部分 / 未满足 / 待核验 |

实质错误单独记录为有、无或待核验。记为有时，记下具体断言、反驳证据，以及它对用户判断或操作的影响。以下任一情况一经确认，即为实质错误：

1. 核心结论错误；
2. 关键建议会让用户做错事；
3. 捏造决定性证据；
4. 把未经证实的现场情况断言为已确认事实；
5. 遗漏必要条件，使回答变成错误的无条件结论。

不改变任何判断或操作的笔误和次要措辞问题只做备注。主结论正确、但附带建议有实质错误的，仍属实质错误。正确但无关的额外信息不加分。
<!-- /context:section -->

<!-- context:section id="grades" -->
## 四档结果与判定顺序

| 结果 | 规则 |
| --- | --- |
| 完全解决（`resolved`） | 核心结论正确，需求完全满足，没有实质性误导。 |
| 部分解决（`partially_resolved`） | 交付了有用且正确的内容，但缺少部分请求或必要事实；没有已确认的实质错误。 |
| 实质错误（`material_error`） | 核心结论或关键建议有实质错误，包括误导性的无条件概括和捏造决定性证据。 |
| 未解决（`unresolved`） | 没有实质回答——只给计划、只要求补充信息，或说“无法回答”。错误的拒答本身包含已确认的关键错误时，仍记为实质错误。 |

**顺序：**先排查已确认的实质错误，再判断对需求的覆盖。正确内容不能抵消关键错误。

**待核验**（`pending_verification`）是评审状态，不是第五档。决定性事实暂时无法核实时，保留检查项、暂不定档；绝不能记为通过或失败。如果已有证据确认了实质错误，直接定档。**需要补充信息**是交互状态，可以与某一档并存：只提问题为未解决；先回答一部分再追问，可以是部分解决。
<!-- /context:section -->

<!-- context:section id="fairness" -->
## 公平规则

- 语义等价的短答、长答、列表、表格以及不同的有效证据路径都接受。核对语义和事实，不去匹配参考文本、固定措辞、标题或工具顺序。形式本身不加分也不减分，除非它确实妨碍理解、掩盖了关键条件或造成歧义。
- 只有会改变结论或用户操作的条件才是必要条件。不统一要求版本字段、完整调用链、参数流、边界情况清单或下一步建议。
- 对于“怎样调试”，可执行的方法、前提和步骤就是要交付的内容；Agent 如何搜索不必出现在答案里。
- 对于“列出全部”，核对题目范围内的完整集合——给出几个正确示例可能只是部分解决。用户没问到的旁支话题不算遗漏。
- 用户的假设、数量或术语可能有误。准确纠正前提并回答真正的问题，可以是完全解决。
- 区分静态规则与现场事实。如实承认证据缺口不算错误，但请求中未完成的部分仍要记录。
- 没有引用、没有展示过程或回复较短，都不能作为判定结论错误的理由。只有当用户或统一的测试协议要求提供来源，并且对每种方案都同样告知时，来源才是交付要求。主动给出的引用核对其存在性和支持度，不按数量计分；链接暂时打不开不等于捏造。本地证据存在、链接路径正确、链接能用用户账号打开，是三种不同的检查。

<!-- context:section id="counterexamples" -->
## 反例的用法

评审要问：在题目范围内，是否存在有证据的情形能推翻某个决定性断言，或证明某处遗漏会改变用户的判断？反例必须属于题目范围并影响结论——不要临时扩大题目。答案不必专门写一节“反例”；正确的条件或范围表述就足够。没有提到某个分支本身不是错误。保持了范围、没有错误概括、但漏掉部分请求的回答，判为部分解决。

<!-- context:section id="calibration-examples" -->
## 三类校准示例

这些示例改写自真实的判分决定，已去除所有业务细节。

**“定义存在”不等于“发生调用”。***前端在哪里调用了某个旧接口？*代码里保留了请求封装，监控清单里也登记了这个地址，但在核对范围内没有任何地方调用它；页面已改用较新的接口。

- 说明“核对范围内未发现业务调用”即为完全解决。
- 只列出封装、却不判断是否被调用，为部分解决。
- 把监控登记当作发起请求，或断言代码里完全不存在这个接口，为实质错误。
- 只建议怎么搜索，为未解决。

启示：按真实语义和用户意图判分，允许纠正前提，绝不按地址出现的次数打分。

**角色差异还受状态和权限控制。***在某个列表页上，负责人能做哪些非负责人不能做的操作？*实际上每项操作都有各自的条件——角色、流程状态、条目类型——某个详情入口还受开关和组织授权控制，因此非负责人也可能进入。

- 说明差异及其条件，即为完全解决。
- “非负责人看不到任何操作”或“负责人始终可以操作”为实质错误。

启示：反例用来检验无条件概括。必要条件来自题目范围；答案不必展示评审掌握的整条控制链。

**外层选择与内层数据切换是不同的层。***当前流程为新版时，查看旧快照会不会换回旧界面？*父页按*当前*流程选择组件；在组件内切换历史只改变数据。只有另一种组件才会按历史自身的版本渲染，而且修订序号并不等于版本代际。

- 说明这两层，即为完全解决。
- 断言查看历史一定会换回旧界面，或把修订序号当作代际，为实质错误。

启示：已有知识漏掉父层条件时，要回到源码修正判据——不要把知识页当作标准答案。

<!-- context:section id="reviewers" -->
## 评审校准与复核

- 每道题给每个回答一个随机别名并记录随机种子。初评隐藏方案、耗时、工具次数和之前的分数。回答中的链接或措辞仍可能暴露来源，因此要说明匿名是有限的。
- 用单独的校准样例检查一致性：同样的事实写成短版和长版、段落和表格，应得到相同的判定；交换两份回答的展示顺序，判断也不应改变。校准样例与正式题分开存放。
- 复核全部实质错误、待核验、部分解决和边界判定，并抽查完全解决。评审给出别人可以复核的理由；篇幅、文风、工具顺序和是否展示过程不作为统一的加减分项。
- 只有模型评审、没有人工标注样本时，称之为*内部一致性复核*，绝不称为人工校准。
<!-- /context:section -->

<!-- context:section id="statistics" -->
## 分母与统计

- 设冻结题数为 Q、重复次数为 R，每种配置计划运行 **N = Q × R** 次。每档比率都除以 N；部分解决绝不折算为半个。
- 四档数量 + 待核验 + 未运行 = N。已评覆盖率 = 归入四档之一的运行数 ÷ N。
- 交付失败或超时且没有回答的，记为未解决，并保留平台、工具或取消原因；不会自动算作知识错误。
- 默认每题运行三次。只有三次都完全解决的题才计入**稳定解决数**；只有单次运行时，不报告稳定解决率。
- 性能既在全部题上比较，*也*在各方案都完全解决的**共同子集**上比较，并显示各自的分母，避免在不同的、更容易的题上比较各方案。
- 每个改进数字都要标明是**实测**、**条件估算**（附公式与假设）还是**待验证方向**。
<!-- /context:section -->

<!-- context:section id="timing" -->
## 计时

- **主端到端（E2E）耗时** = 测试端收到完整最终回答的时间 − 提交问题的时间。它包括网络、平台初始化、检索、工具、轮询和交付。单位：秒。
- 保存带时区的完整时间戳。跨系统时，说明时钟偏差和精度；缺失值绝不能记为 0。
- 启动、首条进度、首个 token、模型正文完成、运行器结束和用户收到最终回答是不同的事件。按实际采集到的事件命名，绝不互相替代。首条进度消息不是最终回答；任务被标为完成后，仍要确认回答已经交付。
- 如果只有平台创建回执和最终发送回执，就单独报告**平台 E2E**，并标明是代理口径；绝不与接收端 E2E 混在一起。
- 运行前先约定超时上限；600 秒是合理的默认值。它是执行上限，不是业务达标线。超时要记录实际停止时间，重跑使用新的运行 ID；超时绝不能算作一次成功的 600 秒样本。没有最终回答的失败不作为成功交付的延迟样本，但必须呈现其比率和等待时间。
- **平均** = 同口径耗时之和 ÷ 样本数。**P50** = 中位数（偶数个样本取中间两项的平均）。**P90** = 最近秩法，取排序后的第 ⌈0.9 × n⌉ 个值。始终显示样本数；有重复运行时，还要报告每道题的中位数。
<!-- /context:section -->

<!-- context:section id="tools" -->
## 工具调用与渠道开销

- 按唯一调用 ID 统计工具调用，并说明覆盖范围——即平台公开的事件；未公开的子 Agent 的内部调用不计入。一次 shell 调用可能运行多条命令。工具调用描述的是执行路径，不等于模型调用次数或 token。从第一个到最后一个工具事件的时间跨度包含推理、等待和并发，因此不要称之为工具纯耗时。
- 保留平台失败、超时、取消、配额拒绝和重试的原始回执。额外的运行关联到它所重复的那次尝试；绝不用最好的一次替换结果。当某道题需要用户补充信息时，为所有方案定义同一套多轮协议，并标注临时追问和恢复。
- **渠道开销：**为聊天渠道配置的 Agent——例如会拼装回复卡片的 Agent——被直接调用时，仍可能检测渠道、读取卡片说明并解析链接。若要比较纯问答，改用适合直接调用的回复策略，或把这部分开销记录下来并排除。
