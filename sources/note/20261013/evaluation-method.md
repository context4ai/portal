# 知识库测评方法、标准与补充数据（脱敏）

本笔记是 Portal 文档站“测评”分组（测评设计、评分与计时标准、知识检索测评）的来源。内容整理自一次在大型生产全栈 Monorepo 上进行的知识检索测评，只保留可复用的方法、判定规则、统计口径与汇总数据；不包含业务名、接口、路径、仓库、平台名称、账号、任务链接或原题。

## 1. 测什么、不测什么

- 评价用户实际收到的**最终回答**：核心结论是否正确、原问是否得到满足。执行轨迹只用于解释检索、工具和耗时，不要求 Agent 展示内部推理或复述查证过程。
- 质量、端到端耗时、可见工具调用次数**分别报告**，不用任意权重合成一个总分。
- 对比的是**整体方案**：即使模型相同，知识组织、系统提示、工具、权限和运行平台也可能不同，差值不能全部归因于知识库。
- 本轮测的是知识部署后的**作答**。知识生产（生产与更新的质量、耗时、审核负担和成本）尚未测评。

## 2. 参考的业界方法

以下方法是本标准的参考来源；四档结果、采样和记录约定属于项目选择，不宣称为行业统一标准。

| 来源 | 借鉴之处 |
| --- | --- |
| [SimpleQA](https://openai.com/index/introducing-simpleqa/)（OpenAI） | 把回答分为正确、错误、未作答，单独统计“未作答”，不让拒答混进错误或正确 |
| [FACTS Grounding](https://deepmind.google/blog/facts-grounding-a-new-benchmark-for-evaluating-the-factuality-of-large-language-models/)（Google DeepMind） | 先判断是否回应了请求，再核验事实依据；两者分开判定 |
| [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)（Anthropic） | 按产出评估 Agent，不规定固定的工具顺序或路径；保存完整轨迹用于解释 |
| [Ragas Factual Correctness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/factual_correctness/) 与 [Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) | 区分“与参考事实一致”和“与检索材料一致”：材料可能过期或漏条件，与材料一致不等于现实正确 |
| [Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena](https://arxiv.org/abs/2306.05685) | 模型裁判存在位置偏差、冗长偏差与自我偏好；需交换顺序、匿名、用校准样例检查 |
| 最近秩法（nearest-rank）百分位 | P90 取有序样本第 ceil(0.9 × n) 项，结果总是真实样本，便于复核 |

## 3. 可复用的测评流程

1. **建立题集与判据**：从真实用户问题抽样，保留原始表述和必要上下文；每题写一份逐题指南。
2. **冻结对照条件**：固定题面、模型与推理配置、知识与源码范围、系统提示、工具权限、运行区域和日期。
3. **运行并保存证据**：每题新任务、相同题面，保存完整回答、原始工具事件、起止时间与异常。
4. **匿名独立判定**：随机别名，隐藏方案、耗时、工具次数与历史分数，按四档判定。
5. **复核与解释**：复核全部非完全解决与争议，抽查完全解决；解开映射后再结合轨迹归因。
6. **发布可复查结果**：四档数量与分母、平均/P50/P90、工具次数、样本与协议范围，以及局限。

每次变更（题集、指南、配置）使用新版本与新的结果目录，保留旧材料；复跑不覆盖旧结果。

## 4. 准备题集

1. 从真实用户问答抽样，忠实保留问题、必要上下文和术语。相连的追问可以合并成一次冻结输入，但不能插入答案提示、来源路径、额外定位词或评分要求。
2. 每题给稳定 ID 并保存原始出处。被测输入只包含用户问题，不附题号、历史答案、评分表或参考证据。
3. 图片若不能统一输入，转成尽可能忠实的文字；不可读处标“未知”，不猜测。缺图导致无法作答的题先排除，补齐后再纳入新版本。
4. 区分规则说明、代码查证与现场排障三类题。用户没给出的线上权限、部署版本、真实请求，不能暗中补成题目条件。
5. 冻结正式题单并记录哈希。被反复用来改提示或补知识的题标为**回归集**，另设未见过的**保留题**检查泛化。
6. 题型覆盖实际提问分布，例如：接口与页面定位、业务交互规则、接口与参数、权限与角色、版本与调用关系、调试与环境。

## 5. 逐题指南

每题一个文件，包含：

- 原始测试输入；
- 核实日期、来源版本（固定提交）与尚未核实的范围；
- 已确认的参考事实，以及影响结论的成立条件；
- 原问必须交付的事项；
- 可接受的等价表述、多种有效解法，以及**不强求**的内容；
- 四档的具体判据，和能推翻错误断言的反例；
- 可复核的证据位置、它支持的具体事实与已知缺口。

参考答案用于核实事实，不规定回答的篇幅、章节、引文数量、工具调用顺序或完整查证链，也不是要求逐字复现的模板。必要结论只存在于内部过程、没有交付给用户，不计完成。决定性事实无法核实时标“待核验”，不能用旧助手答案或知识页的措辞代替证据。后续发现指南有缺漏，记录勘误与证据，不因回答与旧指南不同就直接判错。

## 6. 质量标准

### 6.1 两个主指标与实质错误

| 指标 | 判定内容 | 记录值 |
| --- | --- | --- |
| 核心结论正确性 | 已给出的关键结论在题目适用范围内是否成立；是否遗漏使结论失真的必要条件 | 正确 / 存在实质错误 / 无可判定结论 / 待核验 |
| 原问需求满足程度 | 用户要求的事项是否得到实质交付；只按原问和必要上下文判定 | 完全 / 部分 / 未满足 / 待核验 |

实质错误单列：有 / 无 / 待核验。有错误时记录具体断言、反驳证据和对用户判断或操作的影响。以下任一情况得到确认即为实质错误：

1. 核心结论错误；
2. 关键操作建议会让用户做错事；
3. 捏造决定性证据；
4. 把未经证实的现场情况断言为已确认事实；
5. 遗漏必要条件，形成错误的无条件结论。

不改变判断和操作的笔误、次要表述问题只做备注。主结论正确但附带建议有实质错误，仍归为实质错误。正确但无关的额外信息不加分。

### 6.2 四档结果与判定顺序

| 结果 | 判定 |
| --- | --- |
| 完全解决 resolved | 核心结论正确，原问需求完全满足，没有实质性误导 |
| 部分解决 partially_resolved | 已交付有用且正确的内容，但遗漏部分请求或必要信息；没有已确认的实质错误 |
| 实质错误 material_error | 核心结论或关键建议有实质错误，包括误导性的无条件概括或虚构决定性证据 |
| 未解决 unresolved | 没有实质答案，只给执行计划、只要求补充信息或说无法回答；错误拒答本身包含已确认关键错误时仍记实质错误 |

判定顺序：先排查已确认的实质错误，再判断需求覆盖。正确内容不能抵消关键错误。

“待核验”（pending_verification）是评审状态，不是第五档：决定性事实暂时无法核实时保留检查项、暂不定档，不能填成通过或失败；已有证据确认实质错误时可以直接定档。“需要补充信息”是交互状态，可以与部分解决或未解决并存：只提问题为未解决，先答部分内容再追问可为部分解决。

### 6.3 公平规则

- 语义等价的短答、长答、列表、表格和不同的有效证据路径都接受；按语义和事实核验，不匹配整段参考答案、固定措辞、章节或工具顺序。表达形式不加减分，只有实际妨碍理解、掩盖关键条件或形成歧义时才记录影响。
- 只有影响结论或用户操作的条件才是必要条件；不统一要求版本字段、完整调用链、参数流、边界清单或下一步建议。
- 用户问“怎样调试”时，可执行的方法、前提和步骤属于交付；Agent 如何检索和核查不必出现在答案里。
- 用户要求“全部”时核对题目范围内的完整集合，几个正确示例仍可能只是部分解决；原问没要求的旁支不算漏答。
- 用户问题中的假设、数量和术语可能有误；准确纠正前提并回应真实问题可以完全解决，不要求迎合用户假设。
- 区分静态规则与现场事实。正确承认证据缺口不算答错，但未完成的用户请求仍要记录。
- 没有引用、没有展示过程或回复较短，都不足以认定结论错误。用户或统一测试明确要求来源时，来源才是交付要求，并须对各方案一致告知。主动给出的引用核对存在性与支持度，不按数量加分；暂时无法访问不等于伪造。本地证据存在、链接路径正确、用户账号线上可打开是三种不同检查。

### 6.4 反例的用法

评审问：在原问范围内，是否存在有证据的情形，能推翻决定性断言，或证明遗漏会改变用户判断？反例必须属于题目范围且影响结论，不临时扩题；不要求答案专门写“反例”章节，正确的条件表述或范围限定即可。没提到某个分支本身不是错误；保留了范围、没有错误概括但漏了用户要求的一部分，判部分解决。

### 6.5 三类校准示例（已改写）

- **“定义存在”不等于“实际调用”**：问某个旧接口在前端哪里调用。代码里保留了请求封装，并在性能统计清单里登记了该地址，但核对范围内没有业务调用，页面已改用新版本接口。正确说明“核对范围内未发现业务调用”即可完全解决；只列封装位置却不判断是否调用为部分解决；把统计登记当成发起请求，或断言旧接口在源码中完全不存在，为实质错误；只给搜索建议为未解决。启示：评估真实语义与用户意图，允许纠正问题前提，不按地址命中次数打分。
- **角色差异还受状态与权限控制**：问负责人与非负责人在某个列表页看到的操作有何不同。实际上几类操作各有身份、流程状态、类型或合同等条件，详情入口还受开关和组织授权控制，非负责人也可能进入，另一项操作只看状态和接口权限。准确说明差异与条件可完全解决；“非负责人所有操作都不可见”或“负责人无条件可操作”为实质错误。启示：反例用来检查无条件概括；必要条件来自用户问题的范围，不要求答案展示评审掌握的全部控制链。
- **外层组件选择与历史数据切换**：问当前流程为新版时，查看旧版本的历史快照是否会换回旧版界面。实际是父页先按当前流程选择精简组件，组件内部切换历史只换数据，不会让父页换回旧界面；普通组件内部才按历史流程版本渲染传统节点；历史修订序号也不等于流程代际。说明两层控制可完全解决；断言历史必定换回旧界面或把序号当代际为实质错误。启示：已有知识若漏了父层条件，要回读源码修正判据，不能机械把知识页当标准答案。

### 6.6 评审校准与复核

- 每题随机分配回答别名（记录随机种子），初评隐藏方案、耗时、工具次数和历史分数。回答自身的链接或措辞可能暴露来源，应说明是有限匿名。
- 用独立的校准样例检查：同一事实的短版与长版、段落与表格应同档；交换两份回答的展示顺序后判断应一致。校准样例与正式题分开保存。
- 复核全部实质错误、待核验、部分解决和边界争议，抽查完全解决。裁判必须给出可复核的理由；长度、文风、工具顺序、是否展示查证过程不作为统一加减分项。
- 只用模型评审、没有人工标注样本时，只能声明“内部一致性复核”，不能称“人工校准”。本轮即为此情况：三名同模型评审各负责 8 题的全部回答，主审复核。

## 7. 统计与分母

- 设冻结题数为 Q，每题重复次数为 R，每种配置的计划运行数 N = Q × R。四档比例都除以 N，不把部分解决折算半分。
- 四档数量 + 待核验 + 未运行 = N；已评覆盖率 = 已归入四档的运行数 / N。
- 交付失败、超时且没有答案：质量记未解决，同时保留平台、工具或取消原因，不自动归为知识错误。
- 默认建议每题 3 次、并发 1、交错方案顺序（记录顺序或随机种子）。每题三次都完全解决才计入“稳定解决数”；只有单次数据时不能报告稳定解决率。
- 性能同时比较全部题与**各方案共同完全解决的同一组题**，并显示分母，避免比较难度不同的“各自答对的题”。
- 优化数字分三类标注：实测、条件估算（写出公式与假设）、待验证方向。

## 8. 计时与工具次数口径

- **主端到端（E2E）** = 测试端收到完整最终回答的时间 − 开始提交问题的时间，包含网络、平台初始化、检索、工具、轮询与交付。单位秒。
- 保存完整时间戳与时区；跨系统时说明时钟偏差与精度，缺失不能填 0。
- 启动、首条进度、首个 Token、模型正文完成、运行器结束、用户收到最终回答是不同事件，按实际采集的事件命名，不能互相替代。首条进度消息不能当最终答案；平台标记完成后仍要确认已交付正文。
- 只有平台创建与最终发送回执时，单列“平台 E2E”并标明代理口径，不与接收端 E2E 混算。
- 超时上限运行前约定，默认可从 600 秒起；这是执行上限，不是业务达标线。超时记录实际停止时间，重跑保存新的运行 ID，不能把超时写成成功的 600 秒样本；失败且无最终答案不作为成功交付的延迟样本，但失败率和等待必须呈现。
- 统计：平均 = 同口径耗时之和 / 样本数；P50 = 中位数（偶数取中间两项平均）；P90 = nearest-rank，排序后第 ceil(0.9 × n) 项。始终显示样本数；多次重复时还应报告每题中位数。
- 工具次数按唯一调用 ID 去重，注明覆盖范围（平台公开事件，未公开的子 Agent 内部调用不计）。一条 shell 可能包含多个命令；工具次数描述执行路径，不等同于模型调用次数或 Token。工具首末事件跨度包含推理、等待与并发，不能称为工具纯耗时。
- 平台失败、超时、取消、配额拒绝和重试保留原回执；额外重跑关联原试次，不挑最好的一次覆盖。涉及用户补充信息时统一定义多轮协议，临时追问和恢复要明确标注。
- 渠道开销：若被测 Agent 配置了面向聊天渠道的回复策略（例如拼装消息卡片），直接调用测评时它仍可能执行渠道检测、读卡片说明、解析链接等步骤。比较纯问答时应改用适合直调的回复策略，或单独记录并排除这部分开销。

## 9. 归因分类

解开方案映射后，结合原始工具轨迹把差距归为：事实材料有误、知识遗漏关键条件、检索遗漏、搜索范围判断错误、推断或归纳错误、答案漏交付、证据不可达、流程重复或渠道开销、等待启动。日志只能支持它实际显示的行为；相关性不自动证明因果；不把更多工具调用当更认真，也不把更快当更准确。

## 10. 交给 Agent 设计测评时的产出物

为目标业务产出：问题文档（含出处）、独立的评分标准、逐题指南、采集计划（配置、次数、顺序、超时、记录字段）、原始记录目录、汇总报告。先冻结题目与判据，再运行助手。新业务必须自行核实来源、题目适用范围、必要条件和反例，不沿用其他业务的事实判断。

## 11. 补充数据：同一知识配置下的模型对比

| 指标 | GPT 5.6 SOL Medium（首轮） | Grok 4.7 | Claude Opus 5.5 |
| --- | ---: | ---: | ---: |
| 完全解决 | 21 / 24（87.5%） | 23 / 24（95.8%） | 23 / 24（95.8%） |
| 部分解决 / 实质错误 | 2 / 1 | 0 / 1 | 0 / 1 |
| 平均 / P50 / P90 端到端 | 157.1 / 136.8 / 256.2 秒 | 304.0 / 314.2 / 465.9 秒 | 139.3 / 141.4 / 188.7 秒 |
| 平均可见工具调用 | 24.5 | 40.3 | 11.6 |
| 启动观测均值 | 31.8 秒 | 34.4 秒 | 40.0 秒 |

- 三种模型共同完全解决 20 题：平均端到端 SOL 162.8 秒、Grok 312.7 秒、Opus 142.3 秒；平均工具调用 25.4 / 41.3 / 12.2。
- Opus 相对 SOL 24 题中 18 题更快，P90 降低 26.3%，工具调用减少 52.6%；Grok 24 题均慢于 SOL，工具调用多 64.0%，更长的调查路径没有带来更高的完全解决率。
- 完全解决数相同不代表同题等价：两款新模型各修复了首轮的部分缺口，也各引入了一项不同的错误。
- 同一结论可以由长短不同的路径得到：某题两者都正确，一个模型 493.7 秒 / 75 次调用，另一个 176.4 秒 / 18 次调用。

## 12. 补充数据：错误与开销归因

- **搜索范围判断错误**：在稀疏检出的工作树里没检出调用方目录，却用局部搜索结果推断“全仓无引用”。看过源码不等于搜索范围完整；全仓否定结论前要先确认检出范围。
- **归纳条件错误**：知识对直接调用写明了某个地区，对动态表单保留了按字段调用；回答把前者推广到所有请求，源码中另一个地区的字段构成反例。不是因为“没展示过程”被扣档。
- **有针对性的来源核查奏效**：首轮漏掉父页分支条件的一题，后续两个模型都追到了父页的组件选择与历史数据切换，纠正了结论。
- **渠道准备开销**：直接调用时，被测配置仍按聊天渠道场景执行卡片相关步骤。首轮 24 题共 54 次可见相关调用；另一模型每题都做链接解析和渠道上下文检查，去重 149 条，占其工具总数 15.4%。这些不等于成功发送卡片，也没有单独分离耗时；按入口尽早裁剪投递准备可以减少与作答无关的步骤。
- **启动等待**：托管平台从提交到首次观察到“运行中”约 32 秒（含轮询粒度）。条件估算：把首轮每题实测启动替换为假设目标、其余阶段不变（估算 E2E = 实测 E2E − 实测启动 + 假设启动目标），目标 5 秒时平均 130.4 秒、P50 105.5 秒、P90 229.9 秒；目标 10 秒时 135.4 / 110.5 / 234.9 秒。是否可达需按同题同配置复测。
- **协议差异**：后两轮每模型最多并发 4，首轮最多 2 且部分串行；日期、技能、运行环境和部分读取版本也不同，不能把全部差值归为模型本身。
- 后续改进重点：全仓否定结论前验证检出范围；知识合并时保留分支条件；直接会话跳过没有投递对象的卡片准备。
