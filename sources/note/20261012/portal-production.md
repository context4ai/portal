# 本站如何用 Context 生产

本笔记是 Portal 文档站原理“Agent Graph › 在 Context 中的应用”中 “Built with Context” 一节的来源，记录 context4ai.org 文档站自身的生产方式。只包含社区仓库与本站公开的事实。

## 工作区

- Portal 仓库根目录就是 Context 知识工作区：`package.json` 声明工作区，`src/index.ts` 登记来源与输出，`src/indexers.yaml` 写明各组读者需求，`src/knowledge-map.yaml` 是导航结构。
- 来源：三个社区仓库，各自固定到一个提交（Context 先固定在 `v0.7.60`，最后一个阶段前更新到 `v0.7.61`；Agent Graph 固定在 `v0.3.0`；Source Graph 固定到一个没有发行号的提交）；另有五篇脱敏笔记（使用经验、压缩比实测、检索测评汇总、知识服务 Agent 设计、常见问题），每篇由维护者审阅后登记。
- 输出：一个知识包 `context-kb`，构建出 `/context/` 文档站（英文为主语言，简体中文为译文）和 LLM Docs。首页 `/` 是仓库里另一个独立的静态页面。

## 流程

1. 规划：来源涉及三个仓库，按 `context-plan` 先调研，写出 PLAN 报告，把全站分为六个阶段：入门与 Context 原理；登记来源、生产、审核、更新与查询指南；输出与站点、Indexer、知识服务、工作区维护与实践指南及 Context 参考；Source Graph；Agent Graph；“更多”菜单与首页链接。另插入一轮修订，补写七篇并统一称呼与链接。
2. 每个阶段：`task prepare` 与 `task resume` 开启新的生产阶段，Agent 按读者问题分批写作；每篇文章分节，每节登记指向源码行或笔记的来源引用，提交时校验格式、链接与引用。
3. 审核：生成 HTML 审核报告，检查导航是否全部挂好、图表能否渲染，再批准。前两个阶段由维护者审核；之后维护者把审核委托给 Agent，由 Agent 逐篇核对来源后批准，发现事实偏差时走 `revise` 修订已批准页面。
4. 翻译：批准后的文章和导航标题由多个子 Agent 并行译成简体中文，脚本核对分节标记、代码块、链接与行内代码不变后提交。
5. 版本：每个阶段记录一个工作区版本与 Changelog（从 0.1.0 起逐阶段递增），然后构建站点与知识包，本地预览。
6. 全部阶段完成后，提交 Portal 仓库并部署网站。

## 观察

- 同一个公开入口贯穿全部阶段：每次中断或换会话后，Agent 都从 `context status` 返回的当前 Route 继续，不依赖对话记忆。
- 写作中多次发现初稿与源码不符（例如超时返回的错误码、匿名限流按什么计数），都在提交前对照源码修正；来源引用让这类核对可以逐节进行。
- 修订已批准页面只改受影响的分节，不重新生产整篇。
- Context 来源从 `v0.7.60` 更新到 `v0.7.61` 时，`context verify` 按引用的源码区域列出内容有变化或位置移动的页面，`context update` 把这些页面作为候选，Agent 逐页判断是否需要修订；“更多”菜单的新页面也作为同一次更新的新主题写成。
