# Context 使用经验（脱敏）

本笔记是 Portal 文档站入门“复杂任务”与指南“实践”分组的来源，整理自团队在大型研发组织中使用 Context 的经验。不包含内部平台、账号、链接或业务数据。

## 六步流程中的经验

- 初始化后先自由对话，把知识的内容、来源（文档链接、仓库地址、关注的模块等）和期望形式讲清楚。Agent 会调研并反问，直到形成开工报告。开工报告包含已确认的配置与范围、规划内容，以及预计产出的知识包或站点布局。
- 生产阶段耗时较长，平均每个任务约 1 分钟。Agent 会持续反馈进度与任务总数；过程中可以随时要求本地预览。
- 发布后确认知识包与其他产物，Agent 会把工作区提交到 Git，结束本次生产。

## 复杂任务

- 工作量特别大的任务会先进入规划：每批规划不超过 30～50 篇文档。每批完成生产、发布并更新计划文档（`PLAN-*.md`）且提交后，才进入下一批。
- 大规模任务要及时预览开工报告与变更页面，不满意就提出修订要求（话术、反例、风格）。越早纠偏，最终质量越高。

## 审核报告的三个判断点

审核报告直接决定产出知识的范围与质量，审阅时判断三点：

1. 知识的结构（主题划分、目录、文档）是否符合预期。
2. 知识的内容（写作意图、风格等）是否符合预期。
3. 是否还有相关内容需要纳入范围，或有不需要的内容应当剔除。

## 规模化后重整目录

初版的文章标题往往偏抽象，目录名称和结构也不理想。知识达到一定规模后，可以要求 Agent 重新调研已入库的知识体系，给出更易读、直观的目录与文章结构，此时效果比规划阶段更好。然后修订并再观察一轮。修订的成本远低于重新生产，适合结构与内容的微调。

## 文档落后代码

生产时会交叉比对不同来源，而文档落后于代码是常态。Agent 默认以代码事实修订知识。如果希望同时修正上游文档，可以在任务开始时或工作区的 `AGENTS.md` 里加一条要求：

```text
发生“文档落后代码”的修订时，记录到 update-remote/<日期>-<主题>.md，包括上下文、判断与修订建议。
任务结束后统一处理 update-remote 中的待办：找到对应的上游文档，完成修订，或给出精简的修订建议（由用户决定）。
```

这样上游文档能及时更新，也避免知识与上游长期分叉。

## 模型选择

- 首选主力（如 Claude Opus 5.5）：首次创建、日常生产与检索都适用，速度约为其他模型的 2～3 倍，消耗反而更低。
- 均衡模型（如 GPT 5.6 SOL、Grok 4.6）：速度与成本适中，适合文本、代码与中等强度的代码探索。
- 低成本快速模型（如 DeepSeek 4.1 Flash）：适合面向人阅读的文档处理与代码总结。
- 高阶模型（如 GPT 6.0 Astra）：适合首次创建超大型知识库时的规划与代码深度归因，成本高；Context 内置的多 Agent 调度会自动并行工作。
- 问答阶段，同等质量下不同模型的耗时差异可达两倍以上，见测评汇总笔记。

## 迁移已有知识库

已有 LLM Wiki、Skills 等形式的知识库时，建好工作区后可以这样开始：

```text
请调研 Context 的功能，然后迁移当前的知识库：

- 当前知识库的地址、内容与文档范围：
- 当前知识库的生产方式（脚本、提示词等）：
- 期望发布的结构与形态：保持现状，或新的要求
- 历史答疑问题或测评问答集，用于了解知识库的使用场景与目的

根据以上信息形成调研报告，推进到开工报告后暂停，我来审阅方案并规划工作批次。
```

## 常用提示词

| 场景 | 说法 |
| --- | --- |
| 开工 | 在 `<目录>` 初始化 Context 工作区，为 `<仓库或模块>` 和 `<文档链接>` 建立知识库，先调研再给我开工报告 |
| 补充材料 | 把 `<新材料>` 加入来源，重新规划受影响的部分，给我新的开工报告 |
| 修订 | 修订 `<文章>`：`<问题>`，保持来源引用 |
| 重整结构 | 重新调研已入库的知识，给出更直观的目录与标题方案，确认后再修订 |
| 更新 | 来源已更新到 `<版本>`，定位受影响的知识并复核更新 |
| 评测 | 用 `<题集>` 评测当前知识库，按判据四档评分并给出 P50/P90 |

## 评测知识库效果

问答质量与效率取决于知识的准确性、完整性与证据关联，也受模型能力、运行环境、检索规划与工具执行方式影响。评测时用真实问题建题集，与其他方案或自身优化前的版本对比，再结合运行轨迹定位问题：知识缺失、关键条件遗漏、重复检索、启动等待或工具开销。方法细节见测评汇总笔记。
