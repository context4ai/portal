# 知识检索测评汇总（脱敏）

本笔记是 Portal 文档站“测评结果”与“模型选择”篇章的来源。原始测评来自一个大型生产全栈 Monorepo（前后端知识兼有）的真实开发者问题，本文只保留汇总数据、方法与边界，不包含业务名、接口、路径、仓库、平台、账号或原题。

## 测评对象

评估知识部署后，Agent 回答真实开发者问题的质量、耗时与工具开销。知识生产（生产与更新知识的质量、耗时、审核负担与成本）尚未测评。

## 方案

| 方案 | 知识与检索方式 | 作答模型 |
| --- | --- | --- |
| LLM Wiki | 一次性生成的 LLM Wiki，Agent 在本地搜索与读取文件 | GPT 5.6 SOL Medium |
| Context | Context 知识包，Agent 在本地检索 | GPT 5.6 SOL Medium |
| Context + Source Graph | Context 知识包，代码经 Source Graph 远程读取固定版本 | Claude Opus 5.5 |

LLM Wiki 与 Context 使用相同模型，可直接比较。Context + Source Graph 同时更换了模型，Source Graph 自身的贡献见下文的同模型对照。

## 题集

24 道题，来自真实开发者问题，题集冻结后再运行。每个方案每题运行 1 次。

| 题型 | 题数 | 示例（已改写） |
| --- | ---: | --- |
| 接口与页面定位 | 7 | 某接口在哪些页面调用，是否仍被使用 |
| 业务交互规则 | 5 | 某按钮在什么条件下展示或禁用 |
| 接口与参数 | 4 | 某请求是否会传空参数，在什么条件下 |
| 权限与角色 | 3 | 菜单与权限点的对应关系 |
| 版本与调用关系 | 3 | 新版页面相对旧版新增了哪些接口 |
| 调试与环境 | 2 | 如何在指定环境调试某类项目 |

## 评分方法

- 每题事先写好判据，评审按判据给出四档：完全解决、部分解决、实质错误、未作答。
- 评审由模型完成（GPT-6 Astra Ultra），评审时不知道答案来自哪个方案；未经人工校准。
- 耗时取调用端观察到完整回答的端到端时间，统计平均、P50 与 P90（nearest-rank）。
- 工具调用只统计 Agent 可见的调用次数。
- 为排除题目难度差异，另取三个方案都完全解决的题目作为共同子集比较。

## 同模型对照

同为 Claude Opus 5.5 时，Context 本地检索为 23/24 完全解决，平均 139.3 秒，P90 188.7 秒，平均 11.6 次工具调用。加上 Source Graph 后完全解决数不变，平均耗时降低 33.1%；本地的仓库准备、Shell、搜索与读文件共 256 次调用，被 164 次远程检索替代。

远程检索中有 8 次参数校验失败（批量读取字段名写错、使用了不支持的参数、超出上限），Agent 均自行恢复。

## 模型对照（用于模型选择）

同一知识与检索方式下，另一个模型（Grok 4.7）同样完全解决 23/24 题，但平均耗时 304.0 秒，约为 Claude Opus 5.5（139.3 秒）的 2.2 倍。质量相同的情况下，模型选择对耗时影响很大。

## 观察到的现象

- 宿主仓库里找不到目标地址时，知识直接给出“页面 → 远程 SDK → 接口”的链路，Agent 不必在多个仓库间盲目搜索。
- 新旧差异类问题需要先确定“和哪个版本比”；知识记录了来源的固定提交与比较范围。
- 少数错误来自知识遗漏了组件的分支条件，导致概括过度。这类缺口应转为修订任务补齐。
- 工具调用从 77.5 降到 24.5，再降到 7.8：知识减少了盲目探索，远程检索又替代了本地的仓库准备与文件读取。

## 必须随数据披露的边界

- 每题只运行一次，不能据此推断稳定性。
- 比较的是整体方案：LLM Wiki 与 Context 运行在不同的 Agent 环境，系统提示不同；Context + Source Graph 同时更换了模型与 Context 版本，运行日期、并发与超时上限也不同，且属于已见题回归、单一评审。
- 端到端时间包含环境启动与轮询粒度，不包含额度排队。
- 成本为估算值：每题约 56.7 万 → 6.3 万 Token，按标准 API 单价（输入 \$4、输出 \$20 / 百万 Token，不计缓存折扣）折算为 \$2.45 → \$0.27，降低 88.9%。首测版与换模型版为逐请求回放估算，LLM Wiki 与最新版按工具调用次数等比例推算，口径见 [benchmark.md](../benchmark.md)。


## Muse Wonder 与 Opus 的知识问答对照（2026-10-21 补充）

以下为用户提供并要求同步至社区文档的脱敏摘要，仅保留模型名称、汇总指标及解释边界。它补充已有测试，不替换较早的本地检索对照。

在本轮 24 道开发者知识问答中，Muse Wonder + Source Graph 与 Claude Opus 5.5 + Source Graph 整体表现接近：Muse 多完全解决一题，Opus 响应稍快。

| 指标 | Muse Wonder + Source Graph | Claude Opus 5.5 + Source Graph |
| --- | ---: | ---: |
| 完全解决率 | 100%（24/24） | 95.8%（23/24） |
| 平均答复耗时 | 106.9 秒 | 93.2 秒 |
| P90 耗时 | 135.0 秒 | 123.0 秒 |
| 平均工具调用 | 11.7 次 | 7.8 次 |
| 单题预估费用 | $0.210 | $0.272 |

Muse 平均每题慢约 14 秒（15%），本轮全部完成原问要求，可加入知识检索与代码问答的主力候选，作为 Opus 的备选。Muse 实测平均 38.8 万 Token/题；费用是估算参考，不表示已证明实际成本优势。

结论只适用于本组 24 题。运行环境与配置有差异，不能证明两个模型普遍等效，也不能推断跨场景稳定性。选择模型时应使用自己的问题集，同时比较答案质量、平均与尾部耗时和工具调用；本轮没有验证知识生产能力。

- Muse Wonder 实测平均约 38.8 万 Token/题，DeepSeek 约 47.2 万 Token/题；DeepSeek 费用低主要来自单价低。

### 整理时的取舍
