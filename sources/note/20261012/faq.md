# Context 常见问题（脱敏）

本笔记是 Portal 文档站入门“常见问题”的来源，整理自团队使用 Context 知识库时提出的问题与讨论结论。不包含内部平台、人名、链接或业务数据。

## 小模块需要建中心知识库吗？

不一定。中心知识库适合多人共享、远程使用的场景：统一登记团队的代码仓库、文档与会议记录，供 Bot、知识网站和各成员的编码 Agent 共用同一份经过审核的知识。小模块或单人维护的内容，随仓库放在 `docs/` 中也合适；Context 可以把同仓库文档登记为仓库内容，不必复制成知识。

## 知识由 AI 生成，质量怎么保证？会不会越写越膨胀？

人把控大方向，Agent 把控细节：

- 人在审核报告中判断知识分类、更新范围和粒度是否合适，Diff 报告审核通过前不发布。
- 每段结论都登记出处（文件、行号与版本），写入前自动校验引用。
- Agent 在生产和更新中交叉比对不同来源，经常能发现上游文档落后于代码的问题，并按代码事实修订，也可以按要求回写上游文档。
- 知识面向问题压缩来源，只保留回答需要的内容；规模变大后可以让 Agent 重整目录与标题。

## 知识包和 LLM Wiki 有什么区别？

知识包是一个容器，不强制内容的写法。Context 提供一套默认的 Indexer 与写作模式，团队也可以定制自己的知识生产技能，以及知识包里输出给 Agent 的技能。与只有页面的 LLM Wiki 相比，知识包额外带有索引、证据链和面向 Agent 的检索入口；这些目录由知识库迭代自动维护，不需要手工同步。

## 更新流程太长，维护者需要关心哪些步骤？

只需要关心审核。知识仓库提交、知识包构建与站点发布默认静默完成；只有 Diff 审核、权限问题或有异议时才打断维护者。在网站上审完 Diff 报告后流程会直接推进。

## 一次规划了几千篇文档，任务推进不动怎么办？

先规划再生产。来源较多（超过 30 篇或两个以上仓库需要深入调研）时，先产出规划，按批次推进，每批不超过 30～50 篇；来源超过 500 篇时会暂停，请人确认筛选条件。

## 首次问答为什么比较慢？

主要是冷启动：准备运行环境、安装 CLI 与知识包、克隆仓库。运行环境预置这些内容，并用远程检索按 commit 读取代码而不是克隆仓库，可以显著缩短等待。简单问题的响应仍在持续优化。

## 前端和后端的知识可以放在同一个知识库吗？

可以。前后端代码和文档虽然分属不同仓库，但都可以登记为同一工作区的来源；跨仓的业务流程反而更需要一份统一的知识。各端维护者按各自的来源范围参与更新与审核。
